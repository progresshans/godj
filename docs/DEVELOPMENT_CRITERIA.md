# 기능 개발과 사용성 판단 기준

GoDj는 모델 중심 앱을 빠르고 일관되게 완성할 수 있는 통합 프레임워크를 지향한다.
기능을 선택하고 공개 API를 설계할 때 이 문서를 사용한다. 현재 지원 범위는
[구현 현황](status/IMPLEMENTATION_MATRIX.md), 동작 비교는 [호환성](COMPATIBILITY.md),
실행 범위는 [검증 전략](TESTING.md)이 소유한다.
기준의 비교 근거와 한계는 [프레임워크 조사](research/2026-09-12-framework-developer-experience.md)에 있다.

## 제품의 기준점

개발 편의는 첫 endpoint의 줄 수에 더해 프로젝트 시작, 데이터 변경, 권한 적용, UI/API 연결,
실패 진단, 테스트와 업그레이드에 필요한 전체 작업으로 평가한다.
지원하는 기본 경로에서는 프레임워크가 호환되는 구성을 선택하고 연결 책임을 진다.
애플리케이션은 업무 규칙과 공개할 데이터, 권한 정책을 명시한다.

기본 구성이 있다는 것은 모든 의존성을 직접 구현하거나 모든 기능을 실행 시 항상 켠다는 뜻이 아니다.
공식 기본 경로의 조합과 수명은 GoDj가 검증하고, 별도 선택이 필요한 기능은 지원 범위와 함께 드러낸다.
일반 작업에서 내부 adapter·runner·descriptor의 구조를 먼저 이해해야 하는 곳은 사용성 개선 후보로 본다.

참고 대상은 판단하는 문제에 따라 구분한다.

| 판단하는 문제 | 기준의 역할 |
|---|---|
| 모델·관계·ORM·migration·Form/Admin의 통합 경험 | Django의 개념과 동작, GoDj 헌장 |
| 이미 채택한 API validation·partial update·인증·오류 의미 | 고정된 DRF contract와 명시적 deviation |
| 간결한 typed endpoint·요청/응답·문서·client 연결 | FastAPI, Django Ninja, Django Modern REST의 사용성 사례; Go 표현은 Huma 등도 참고 |
| HTTP·OpenAPI·보안 protocol | 해당 표준과 GoDj가 명시적으로 선택한 계약 |
| 타입·취소·동시성·자원 수명 | Go의 compile/runtime 의미와 현행 소유권 계약 |

참고 프레임워크가 늘어도 모든 동작을 동시에 호환하거나 모든 oracle을 추가하지 않는다.
외부 결과를 계약으로 채택할 때만 버전·source·관찰 범위를 고정한다.
사용성 비교는 API 형태의 설계 근거이며 기존 계약의 실패를 면제하는 사유가 아니다.

## 우선 평가할 사용자 흐름

다음 흐름 중 실제 다음 요구 하나를 고르고, 필요한 범위만 구현한다. 목록 전체가 한 작업의 필수 범위는 아니다.

| 흐름 | 완료 시 확인할 내용 |
|---|---|
| 새 앱 시작 | 문서화한 기본 설정으로 DB 준비·migration·초기 운영자·서버 시작까지 연결되고, 재시작이 데이터를 다시 만들지 않음 |
| 모델 성장 | 필드나 관계 변경이 ORM·migration·선택한 Form/Admin/API에 일관되게 반영되고 기존 데이터 처리도 설명됨 |
| 권한 있는 조회·쓰기 | 인증, 목록 범위, 객체 접근, 입력 가능한 관계, 생성·수정·삭제 정책이 필요한 모든 경로에 적용됨 |
| 일반 CRUD와 업무 명령 | CRUD의 반복 연결을 줄이면서 승인·종결 같은 명령은 명시적인 업무 동작과 transaction으로 표현됨 |
| API와 client | typed 입력·출력·오류·인증 정의가 실제 HTTP와 OpenAPI에 일치하고 대표 client가 사용할 수 있음 |
| 실패와 유지보수 | 잘못된 입력·취소·충돌·지원하지 않는 변경의 원인과 다음 행동을 알 수 있고 테스트에서 재현 가능함 |

Article와 Category–Ticket Helpdesk를 우선 소비자로 사용한다. 다중 사용자·댓글·범용 scaffold·OpenAPI는
현재 구현됐다고 가정하지 않는다. 기능을 범용이라고 주장할 때는 구조가 다른 모델과 필요한 cross-app 흐름을 확인한다.

## 설계 평가

### 1. 모델 의미와 표현 정책

모델의 타입·nullable·길이·기본값·관계는 Schema IR에서 가져온다.
공개할 필드, 요청과 응답의 차이, 읽기 전용 값, 업무 권한과 HTTP 상태는 명시적인 표현·동작 정책이다.
모델 정의만으로 이 정책을 추측하거나 모든 필드를 자동 공개하지 않는다.

모델 기반 API와 DB 모델이 없는 검색·집계·업무 명령의 요청/응답을 모두 표현할 수 있어야 한다.
동일 의미의 선언은 재사용하고, DB 모델과 생성 입력·응답·PATCH가 의미상 다르면 각각의 차이를 표현한다.
별도 타입이 있다는 이유만으로 중복이라고 판정하지 않는다.

### 2. 타입과 선언의 연결

필드 접근과 handler 연결에서 Go 타입을 보존하고 가능한 오류는 compile 또는 시작 시 검증한다.
코드 생성으로 반복 연결을 줄여도 생성물은 결정적이며 실패 시 이전 정상 결과를 보존해야 한다.
단순한 작업에서 문자열 키를 여러 번 적거나 같은 schema를 다른 형식으로 반복 작성해야 하는지 확인한다.

구체적인 endpoint DSL, struct tag 사용, 생성 방식, DI container 도입은 이 문서에서 확정하지 않는다.
기존 경계 위의 작은 소비자 흐름으로 장단점을 확인한 뒤 필요한 API를 선택한다.

### 3. API 실행과 문서의 일치

API 확장 시 요청의 위치·타입·필수 여부, 응답·상태 코드, 예상 오류와 인증 정보를 함께 설계한다.
OpenAPI 생성 기능을 구현하기 전에도 같은 정보가 실제 실행과 문서에 연결될 수 있는지 확인한다.
보안·read-only 선언이 문서에 있다는 사실만으로 runtime에서 적용됐다고 보지 않는다.

Schema IR은 모델 의미를, API 선언은 경로·operation·노출·응답 정책을 소유한다.
OpenAPI를 만들기 위해 모델 의미의 별도 원본을 추가하지 않는다.
Middleware의 인증·권한·입력 제한 오류도 API 계약의 일부로 검토한다.
지원할 OpenAPI 버전과 client generator는 실제 도구 호환을 확인해 선택한다.

### 4. 기본 흐름과 확장

공통 인증·권한·오류 처리·pagination은 기본 경로에 연결하고 업무 정책은 명시적으로 주입한다.
생성·목록·단건·수정·관련 객체 선택에서 권한의 적용 위치가 다름을 드러낸다.
표준 CRUD는 간결하게 구성할 수 있어야 하고 업무 명령은 불필요한 CRUD 구조 없이 표현할 수 있어야 한다.

의존성은 기본 구성에서 한 번 조립하고 테스트에서 교체할 수 있게 한다.
함수·interface·constructor로 충분한 요구에 거대한 DI 체계를 선행 도입하지 않는다.
필요한 custom handler·query·표현으로 확장할 때도 context, 인증, transaction의 책임이 유지돼야 한다.

### 5. 직관적인 실패와 운영

일반 오류에는 원인 위치와 수정 가능한 정보를 제공한다. Client 응답에는 secret·내부 원인을 노출하지 않고,
개발자 진단에는 비밀을 제거한 원인과 위치를 제공한다. 내부 오류 연결과 안전한 진단 가능성은 보존한다.
Compile/startup 오류, 사용자 입력 오류, 권한 거부, 인프라 실패와 취소를 구분한다.
알 수 없는 설정이나 미지원 동작을 조용히 무시해 편의성을 만들지 않는다.

Go의 context와 명시적 I/O를 사용한다. 백그라운드 실행은 요청 수명과 분리된 별도 소유자를 요구하며,
단순 goroutine 실행을 durable job·재시도·다중 process 전달의 보장으로 취급하지 않는다.
배포 기본 경로는 migration과 serve의 수명, 설정·secret, 종료·관측을 함께 설명한다.

## 유지할 안전 조건

- 생략·null·zero·기본값·PUT/PATCH의 차이와 입력/출력 필드 선택
- 목록·객체·쓰기의 권한 및 Session/CSRF·Bearer의 명시적 경계
- 실제 DB 제약, transaction·rollback·durable outcome과 기존 데이터 보존
- Context 취소, 공유 상태·cache 소유권과 자원 정리
- 생성 후보 검증·결정성·실패 시 이전 정상 결과 보존
- 독립 실제 결과와 비교 근거, 필수 검증 누락·skip의 정직한 표시

이 조건의 회귀를 코드 길이·편의 점수·속도 향상과 상쇄하지 않는다.
새 기능에 해당하는 위험만 [TESTING](TESTING.md)의 적절한 위치에서 검증한다.

## 개선을 판단하는 증거

후보 간 비교는 같은 완료 동작·정책·환경으로 한다. 다음 항목 중 변경과 관계있는 것만 기록한다.

| 항목 | 기록 방식 |
|---|---|
| 조립 비용 | 기본 작업 전에 개발자가 선택해야 하는 도구·정책·연결을 구분하고 그 유지보수 소유자를 적음 |
| 변경 비용 | 필드·권한·응답 하나를 바꿀 때 사람이 수정하는 의미상 독립 선언과 수동 매핑을 비교 |
| 이해·실패 비용 | 처음 보는 소비자가 원인을 찾는 데 필요한 개념, 오류 위치와 다음 행동을 확인 |
| 타입·schema 품질 | 잘못된 연결의 compile/startup 실패, HTTP/OpenAPI 일치, 대표 client의 실제 사용을 확인 |
| 실행 비용 | 같은 DB·입력·쿼리·보안 조건에서 query 수, latency·allocation 등을 필요할 때 측정 |
| 유지보수 비용 | 생성 코드·앱 코드·외부 dependency의 업그레이드 책임과 변경 범위를 기록 |

수정 파일 수·줄 수·테스트 수는 설명 자료일 수 있으나 단독 합격 기준은 아니다.
개발 시간·성능은 직접 측정했을 때만 수치로 주장한다. 공식 예제 검토는 실사용 실험으로 표현하지 않는다.
평가는 `채택`, `보완 후 재검토`, `보류`, `미검증`으로 이유와 근거를 구분할 수 있다.
기존 작업·PR의 설명과 검증 근거를 재사용하며, 별도 평가표나 새 ADR을 매 작업마다 만들지 않는다.

## 다음 기능의 선택 순서

1. 현재 구현과 제한에서 실제 사용자 흐름을 끊는 경계를 찾는다.
2. 기본 설정·반복 연결·모델 변경·오류 진단 중 해당 흐름의 가장 큰 비용을 줄이는 기능을 선택한다.
3. API 기능은 typed 입력/출력과 OpenAPI 연결을 함께 고려하고, 이미 채택한 DRF 의미의 변경 여부를 확인한다.
4. 필요한 제품 코드·생성기·소비자·테스트를 한 묶음으로 구현한다. 기반 개선은 그 요구에 필요한 범위로 제한한다.
5. 관련 검증과 사용성 근거를 남기고 설계·구현·실행 결과를 구분한다.
   실행 상세는 Evidence 한 곳에 두며 지원 범위·상태가 바뀐 Matrix·CURRENT만 갱신한다.

새 framework 조사, 전체 코드 리팩토링, 모든 후보의 사전 구현은 다음 기능의 상시 선행 조건이 아니다.
