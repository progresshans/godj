## 맥락

ADR-0027은 named reverse ForeignKey의 query-only relation과 owner-instance `ReverseObject`/`RelatedSet` capability를
분리했습니다. A cold related set owns a source-FK exact QuerySet and evaluation cache, so one owner access is SELECT 1,
JOIN 0이고 repeated `All`은 warm I/O 0입니다. REL-012는 owner 세 개를 각각 cold evaluate하는 세 query가 아니라
primary owner query 1 + source batch query 1을 요구합니다.

Locked Django protocol observation은 Author IDs 1,2,3과 Post fixture에 대해 exact
`[(1,[10,11]),(2,[]),(3,[12])]`, statement kinds `[SELECT,SELECT]`, total SELECT 2, batch predicate column
`author_id`, batch key count 3, JOIN 0, related-access extra 0 and unchanged DB state입니다. Bound-argument vector와
mutation count는 protocol fields가 아닙니다. Exact sorted args `[1,2,3]`, source-PK order and mutation-free trace는
successful adapter publication 전에 통과할 Go compiler/product internal false-green gates이고 oracle/static/protocol
shape/bytes는 그대로 둡니다. Django 내부 prefetch cache/object identity나 SQL 문자열을
복제할 필요는 없지만, GoDj가 공개하는 wrapper/cache는 같은 외부 query count와 ordered result를 안전하게
재현해야 합니다.

Current query Condition은 scalar `Value` 하나만 소유합니다. IN을 comma-encoded string이나 repeated OR로
표현하면 field kind, immutable clone/equality와 exact bound argument list를 잃습니다. Current reverse object
`From`을 owner마다 호출하면 cold set은 만들 수 있지만 batch rows를 atomic하게 여러 cache에 주입할 public seam이
없습니다. Existing Manager/QuerySet/ReverseObject를 widen하면 prior public ABI와 generated bytes까지 소급 변경됩니다.

## 결정 기준

- Primary owner query와 batch source query ownership을 명시적으로 분리
- Existing ReverseObject/RelatedSet/Manager signatures와 semantics, prior generated bytes 보존
- Field-kind-aware immutable IN list and deterministic SQLite argument order
- Caller-order owner snapshots, sorted/deduped bounded keys and source-PK ordered groups
- Missing/invalid owner state와 oversized batch는 backend I/O 전에 fail-close
- Every row membership validated before any warm state is observable
- Failure/cancellation nil output, rows close exactly once, partial publication 0 and retryability
- Duplicate PK inputs share only query key, not wrapper or evaluation state
- No background work, cross-call singleflight, chunking or public cache mutation seam
- Project package only owns concrete cross-app wrapper composition and import edges
- REL-012-only manifest transition and exact old-byte/revert false-green gates

## 고려한 선택지

### Existing `ReverseObject.From`를 owner마다 호출

API addition 없이 동작하지만 owner 수만큼 cold query를 실행합니다. REL-012 exact one batch query와 extra-access 0을
동시에 만족하지 못하므로 채택하지 않습니다.

### Manager/QuerySet에 public `Prefetch` 또는 cache setter 추가

General eager graph와 public cache injection semantics를 한 번에 고정하고 unrelated model query API를 넓힙니다.
REL-012보다 훨씬 큰 결정이며 arbitrary filtered/ordered cache meaning과 invalidation도 필요합니다. 별도
`ReversePrefetch` capability로 제한합니다.

### `ReverseObject` 또는 `RelatedSet` public surface를 변경

Prior accepted API와 exact generated reverse bytes를 소급 변경합니다. New same-package implementation file이
existing private state/queryset cache를 조립하되 public signatures는 그대로 유지합니다.

### IN을 repeated exact OR 또는 encoded scalar로 표현

SQL compiler가 list membership을 식별할 수 없고 empty/NULL/kind validation, list clone/equality와 placeholder
argument order가 불명확해집니다. Condition의 별도 immutable list arm을 채택합니다.

### Owner 입력 순서대로 IN args를 전달

Semantically valid하지만 permutation마다 plan/SQL argument bytes가 달라지고 duplicate input이 batch key count를
부풀립니다. Owner 결과 순서는 별도로 보존하고 query keys는 integer sort/dedupe합니다.

### SQLite parameter limit에 맞춰 자동 chunking

REL-012 exact one batch query를 깨고 partial success/close/error ordering을 확장합니다. 999 distinct keys를 inclusive
cap으로 정하고 1000 이상은 pre-I/O structured failure로 닫습니다.

### Group을 찾는 중 각 cache를 즉시 publish

Later scan/Rows.Err/Close or membership failure가 앞 owner만 warm한 partial state를 남깁니다. 모든 row, terminal
resource and grouping validation 뒤 private ready states를 한 번에 반환하는 all-or-nothing ownership을 채택합니다.

### One shared ready state per duplicate owner PK

Query key dedupe는 가능하지만 derived `OrderBy`/future state ownership과 wrapper pointer independence가 깨집니다.
각 input position마다 cloned values와 distinct ready evaluation state를 만듭니다.

### Existing project reverse generator를 확장

Version/golden/nine product files가 바뀌어 ADR-0027 output을 소급 변경합니다. Separate v1 project prefetch
companion을 채택합니다.

## 결정

### Separate sealed prefetch capability

Exact additive ORM API is:

```go
type ReversePrefetch[Owner, Source any] struct { /* private sealed state */ }

func BindReversePrefetch[Owner, Source any](
	reverse ReverseObject[Owner, Source],
) (ReversePrefetch[Owner, Source], error)

func (p ReversePrefetch[Owner, Source]) Load(
	ctx context.Context,
	backend db.Queryer,
	owners []Owner,
) ([]*RelatedSet[Source], error)
```

`ReversePrefetch` snapshots the canonical private `ReverseObject` state and binds the physical source ForeignKey's
`RelationStorage[Source]`. It is immutable/copyable; each `Load` owns independent evaluation state. The extra storage
capability is validated here only. Existing `BindReverseObject`, `ReverseObject.From`, `RelatedSet` and Manager/QuerySet
public signatures and behavior are byte/semantic locked.

`Load` never issues or hides the primary owner query. Caller passes owners already obtained from the existing QuerySet.
It performs at most one batch source query and never starts a goroutine or coordinates with another `Load` call.

### Immutable IN-list Condition

Exact additive query API is:

```go
const LookupIn Lookup = "in"

func NewInCondition(field FieldRef, values []Value) (Condition, error)
func (c Condition) Values() ([]Value, bool)
```

Condition gains a private pointer to an immutable cloned value-list. The pointer keeps the Go struct comparable; semantic
`Equal` and clone/Plan copy-on-write compare/copy list contents deeply. `Values` returns a fresh clone. `Value` returns the
zero `Value` for every `LookupIn` condition, including scalar-constructor misuse. Existing non-IN scalar condition behavior
is unchanged.

`NewInCondition` requires field name and column nonempty and containing no NUL, and kind exactly integer, string or
boolean. Nullable may be either value; it adds no ASCII/SQL-name restriction beyond existing compiler quoting. It then
accepts only a nonempty list with no NULL and every value's kind exactly matching the field. An invalid/unsupported
FieldRef, empty list, NULL member or wrong-kind value returns `query_error/invalid_plan`; zero field plus zero value cannot
false-pass kind equality. A scalar
`NewCondition(field, LookupIn, value)` is
structurally possible for compatibility but is invalid; SQLite compiler rejects it pre-I/O with
`query_error/invalid_plan`. No public typed `.In`, dynamic `__in`, related filter or general bulk API is added.

SQLite accepts only a valid root-table list-backed IN condition, emits the source field column with one placeholder per
value and binds values in stored order. Relation-path IN, scalar misuse and invalid list state fail before backend query.
Existing scalar exact/isnull/forward/reverse SQL, arguments and error behavior are locked.

### Exact validation precedence and key cap

`Load` runs the following precedence without reordering:

1. nil/typed-nil context -> `query_error/invalid_plan`
2. `ctx.Err()` -> original cancellation/deadline error
3. nil/typed-nil backend -> `backend_error/invalid_plan`
4. zero/corrupt/unbound handle -> `query_error/invalid_plan`
5. clone all owners in caller order; then inspect keys in caller order
   - first absent key -> `query_error/missing_primary_key`, `Field` owner PK field
   - present NULL/non-integer -> `query_error/invalid_plan`
6. sort/dedupe integer keys; 999 inclusive, greater than 999 -> `argument_error/invalid_value`
7. one batch I/O
8. existing scan/Rows.Err/Close/context/backend error precedence
9. complete membership validation/grouping, checking `ctx.Err()` during and after grouping
10. recheck `ctx.Err()` immediately before success-only ready publication

Every pre-I/O owner error returns nil output and issues no query. Explicit integer zero with present=true is a valid key.
Empty owners validate steps 1-4 and then return non-nil empty/0 I/O; owner/key/cap work is absent. Because `db.Queryer` has
no liveness method, an empty call does not prove whether a non-nil backend is open.

Distinct keys are integer ascending in IN args. Owners and results remain caller order. Duplicate PK inputs contribute one
query key but receive independent set pointers, caches and source model clones.

### Batch query and membership validation

The source batch plan is source FK `IN` sorted distinct keys plus source primary key ascending, with JOIN 0. Source rows are
decoded and cloned by the existing sealed descriptor. The bound `RelationStorage` extracts each decoded source's physical
FK and every row is checked against the requested distinct set.

Exact new stable code and taxonomy are:

```go
const CodeRelatedSetMembership = "related_set_membership"
```

- storage `Value(decoded)==false`: `query_error/invalid_plan`
- returned FK NULL or non-integer: `integrity_error/related_set_membership`, `Field` source FK
- returned integer outside requested set: `integrity_error/related_set_membership`, `Field` source FK

`Detail` is diagnostic only. Membership corruption does not use `related_object_cardinality`, and a storage implementation
failure is not mislabeled database integrity. Scan, Rows.Err, Rows.Close, context and backend causes retain existing error
wrapping/precedence. Acquired rows close exactly once.

### Atomic ready `RelatedSet` publication

No returned pointer becomes observable until query iteration, Rows.Err, Close, context and every membership check have
succeeded. Failure returns nil output and retains no partial ready state. Later independent calls retry normally.
Cancellation arriving after batch evaluation but during/after grouping or at the publication boundary is observed before
ready states can be returned.

Each success set has the normal source-FK exact, source-PK ascending cold plan and its own ready evaluation state populated
with only that owner's cloned group. `All` checks nil/canceled context before cache and otherwise returns fresh clones with
I/O 0. `Fresh` and `OrderBy` return independent cold sets; they do not copy the prefetched state. A warm set retains the
backend and can serve cached values after it closes, while a derived cold set reports backend failure. Filtered/custom
warm semantics, public cache injection, chunking and write invalidation are not defined.

Concurrent `All` on one ready set uses existing QuerySet evaluation mutex/clone rules. There is no batch singleflight
across `Load` calls or hidden background lifecycle.

### Separate deterministic project generator

Exact additive generator is:

```go
const ProjectRelationPrefetchGeneratorVersion = "godj-codegen-rel-prefetch-project-v1"

func GenerateProjectRelationPrefetch(
	packageName string,
	packages []RelationReversePackage,
) ([]byte, error)
```

Output publishes `GoDjProjectRelationPrefetchGeneratorVersion`, per-owner prefetch bundles and aggregate binding. Fixture
surface is:

```go
type AuthorsAuthorReversePrefetches struct { /* private objects/posts/reviewedPosts */ }

func (p AuthorsAuthorReversePrefetches) Posts(
	ctx context.Context,
	backend db.Queryer,
	owners []authors.Author,
) ([]*AuthorsAuthorReverseObject, error)

func (p AuthorsAuthorReversePrefetches) ReviewedPosts(
	ctx context.Context,
	backend db.Queryer,
	owners []authors.Author,
) ([]*AuthorsAuthorReverseObject, error)

type ReversePrefetches struct {
	AuthorsAuthor AuthorsAuthorReversePrefetches
}

func BindReversePrefetches() (ReversePrefetches, error)
```

Binding composes `BindReverseObjects` and private runtime handles. Generated bundles cover only the same presence-aware
object-capable owner/reverse set already emitted by `ReverseObjects`; query-only/v3 reverse owners are omitted instead of
being emitted as guaranteed bind failures. Direct runtime prefetch requires an already successful `ReverseObject` bind.
A method first deep-clones the complete owner slice with
the concrete generated descriptor into a private snapshot slice; this pure step cannot fail or perform I/O. It invokes its
corresponding runtime `Load` exactly once on those snapshots **before** constructing wrappers, preserving runtime
context/backend/handle/owner-PK precedence. After a successful batch it calls the existing factory `From` on the same
snapshots, replaces only that relation's private set and returns no wrapper until every defensive construction step
succeeds. Raw owners are never read again after `Load`. After private snapshot completion, subsequent caller-visible alias
mutation cannot change wrapper Model/PK and warm-set matching; callers must synchronize mutation concurrent with the call.
Nonselected relations remain cold. Failure returns nil and no wrapper was publicly observable; duplicates retain
independent wrapper/set identity.

Generation is deterministic under package permutation and gofmt-valid. It reuses canonical reverse reservations
`db`, `orm`, `query`, `ir`, `bool`, `error`, `false`, `nil`, `true`, `init` and every Go keyword, including the already
locked runtime import paths. It adds exact alias/import path `context` and indexed-slice template builtins `make`/`len`.
The package namespace seeds every immutable binding/query/object/reverse prerequisite declaration: version constants,
aggregates, bind functions and all derived types. Each per-owner bundle reserves private field `objects`; a reverse
selector's lower-first private name such as `posts`/`reviewedPosts` must be unique and cannot collide with `objects` or any
fixed/derived field. Adversarial aliases and selector collisions fail with nil bytes. Input normalization, namespace,
unsupported-shape and render/gofmt errors are generator-owned and return nil bytes. A pure generator cannot inspect the
caller's checked-in reverse companion/version; missing or ABI-incompatible `BindReverseObjects` is instead a caller-owned
ten-file union compile/publication failure. Publication preserves last-good output after either kind of failure, and no
same-surface version-constant check is invented. Existing `GenerateProjectRelationReverse`, its v1 version, golden and
exact nine generated relation-product files are byte locked. New `relationprefetchproduct` external compile union is those
nine plus exactly one prefetch companion.

## 결과

### 장점

- REL-012 exact two-query behavior is represented without pretending GoDj has general Django prefetch support.
- IN values, owner snapshots and warm cache publication have explicit immutable/atomic contracts.
- Existing accepted API and generated products remain byte-stable.
- Corrupt source membership cannot leak a partially warm owner collection.
- Local/hosted validation can remain lane-bounded while safety-critical matrix coverage is preserved.

### 비용

- Separate primary query and prefetch call are more explicit than Django's chained QuerySet API.
- 999-key fail-close requires callers to partition externally; automatic chunking is deferred.
- Generated project companion adds a tenth checked-in file and another ABI version pin.
- Only exact `All` cache consumption is warm; derived/custom query semantics intentionally stay cold/unsupported.

### 남은 한계

- This does not implement public `prefetch_related`, custom/nested Prefetch or arbitrary eager graphs.
- REL-009..011, write/delete/DDL/migration and non-SQLite relation behavior remain unsupported.
- Cache invalidation after writes and transaction/session cross-goroutine semantics remain open.
- Q-013 remains `Partial` even after bounded acceptance.
