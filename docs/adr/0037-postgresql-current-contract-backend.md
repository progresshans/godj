## 맥락

GoDj의 actual backend는 SQLite 하나입니다. Core query/write/migration port는 대부분 backend-neutral이지만 AutoField
insert 결과는 SQLite `LastInsertId`에 기대고, migration capability 하나는
`RemoveForeignKeyByTableRemake`라는 SQLite 물리 전략을 이름에 노출합니다. 이 상태에서 PostgreSQL compiler만 추가하면
generated Create의 key 반환, FK 제거 capability와 revision-fenced lifecycle이 backend마다 다른 비공식 경로로 갈라집니다.

PostgreSQL service를 CI에서 시작하는 것만으로는 backend support가 아닙니다. Current generated API로 query/write,
transaction, schema migration, recorder/revision fence와 restart를 실제 실행하고 동일한 오류·소유권 경계를 보존해야 합니다.

## 결정 기준

- Current-only Schema IR/Definition/State와 generated ABI를 바꾸지 않을 것
- SQLite의 기존 SQL/동작과 모든 passing product contract를 보존할 것
- 모든 PostgreSQL user/control object를 explicit schema 아래에서 접근할 것
- SQL injection, `search_path` shadowing과 identifier truncation을 I/O 전에 차단할 것
- Insert key, transaction callback, commit outcome과 retry ownership을 명시할 것
- Schema edit, recorder transition과 revision advance를 한 transaction으로 묶을 것
- 실제 PostgreSQL process/connection restart를 지원 증거에 포함할 것
- Service-only/skip-only job을 false green으로 금지할 것

## 결정

1. Driver는 MIT-licensed `github.com/jackc/pgx/v5` v5.10.0의 `database/sql` bridge를 사용합니다. Public ORM은
   driver type을 노출하지 않습니다.
2. 지원 major는 PostgreSQL 17입니다. Hosted reference profile은 PostgreSQL 17.10, server/database/client UTF8,
   libc `C` locale, `standard_conforming_strings=on`, UTC로 고정합니다. Minor update는 PostgreSQL 정책에 따라
   허용하되 새 reference minor는 실제 gate 뒤 갱신합니다.
3. Public open boundary는 `postgres.Config{URL, Schema}`입니다. Schema는 필수이고 identifier를 strict 검증합니다.
   Connection timezone은 UTC, `search_path`는 `pg_catalog`, `client_encoding`은 UTF8,
   `standard_conforming_strings`는 `on`으로 강제하며 user table, constraint와 control table은 모두
   schema-qualified SQL을 사용합니다. Database locale provider는 libc이고 `datcollate/datctype`는 exact `C`여야
   하며 provider-specific locale override는 허용하지 않습니다.
4. PostgreSQL의 63-byte identifier limit을 silent truncation에 맡기지 않습니다. Table/column/schema/constraint 이름이
   경계를 넘거나 canonical collision을 만들면 I/O 전에 structured invalid-plan 오류를 반환합니다.
5. `query.InsertPlan`은 optional returned key를 소유합니다. Generated Create/Save는 AutoField key를 지정합니다.
   SQLite는 기존 SQL과 `LastInsertId`를 유지하고 PostgreSQL은 `RETURNING <key>`를 사용합니다. PostgreSQL raw insert가
   returned key를 생략하거나 explicit key assignment를 포함하면 첫 packet에서는 pre-I/O unsupported입니다.
6. `MigrationCapabilities.RemoveForeignKeyByTableRemake`는 backend-neutral
   `RemoveForeignKey`로 flag-day rename합니다. Alias/shim은 두지 않습니다. SQLite는 table remake, PostgreSQL은 native
   constraint drop으로 같은 semantic capability를 구현합니다.
7. Type mapping은 AutoField=`BIGINT GENERATED BY DEFAULT AS IDENTITY`, CharField=`VARCHAR(n)`,
   Boolean=`BOOLEAN`입니다. Nullable scalar/FK, empty-source required FK, scalar/FK remove와 model create/delete를
   current normalized state에서만 지원합니다.
8. ForeignKey constraint name은 normalized source table/column에서 deterministic하게 만들고 63-byte 경계를 검증합니다.
   Initial physical action은 framework-owned delete orchestration과 충돌하지 않는 `NO ACTION`입니다.
9. Revision-fenced backend는 dedicated connection과 transaction-level fence를 사용합니다. Applied history/revision snapshot,
   schema operations, exact recorder transition과 revision advance는 같은 transaction에 속합니다. Contended/stale/integrity는
   existing backend-neutral `RevisionFenceError`로 변환합니다.
10. Commit success는 `CommitCommitted`, proven rollback은 `CommitRolledBack`, connection/terminal fault로 결론을 증명하지
    못하면 `CommitUnknown`입니다. Literal COMMIT call이 오류를 반환해도 write가 이미 durable할 수 있으므로
    `CodeCommitOutcomeUnknown`을 반환하고 자동 retry하지 않습니다. 호출자는 재시도 전에 별도 reconciliation으로
    결과를 확인해야 합니다.
11. PostgreSQL error mapping은 SQLSTATE를 구조적으로 사용합니다. English message parsing을 correctness에 사용하지
    않습니다.
12. Support claim은 actual generated CRUD/relation query, Atomic, schema editor, migration recorder/revision, two-connection
    contention, close/reopen와 server restart 뒤 durable resume를 모두 실행한 exact gate 뒤에만 허용합니다.

## 명시적 연결 입력과 소유권

C1의 프로젝트별 불변 설정에 맞춰 URL의 userinfo·authority·path를 사용자·호스트·DB identity의 유일한 원본으로
사용한다. 각 호스트의 생략 포트는 5432, 생략 password는 빈 값이다. 중복 옵션과 query identity override,
잘못된 escape·NUL·64 KiB 초과 입력은 I/O 없이 거부한다. 복수 DNS host와 독립 IPv6 주소는 고정 드라이버가
해석하는 URL 문법 안에서 처리한다. Schema IR·query/transaction·physical-session profile은 바꾸지 않는다.

`pgx` v5.10.0의 [설정 parser](https://github.com/jackc/pgx/blob/v5.10.0/pgconn/config.go)와
[기본값](https://github.com/jackc/pgx/blob/v5.10.0/pgconn/defaults.go)은 process 환경·사용자 홈을 직접 읽으며,
환경 조회를 주입하는 API가 없다. 따라서 adapter가 URL에서 만들지 않은 `PG*` 설정값과 기본 password/TLS 파일 경로를
명시적인 값으로 덮는다. Process 환경을 바꾸거나 전역 mutex로 별도 프로젝트를 직렬화하지 않는다.
Service는 존재 자체로 파일 로딩을 시작하므로 `PGSERVICE`를 Open 전에 거부한다. 검사 뒤 concurrent 변경도
빈 servicefile 경로로 실패하게 하여 다른 service의 설정·credential을 사용하지 못하게 한다.
이는 service 환경에 대한 성공적인 무시가 아니라 명시적인 미지원 오류다.

기본 TLS mode는 `verify-full`이다. 명시적인 `disable`/`allow`/`prefer`/`require`/`verify-ca`/`verify-full`의 의미는
드라이버가 소유한다. URL의 `sslcert`, `sslkey`, `sslrootcert`, `sslpassword`, `sslsni`, `sslnegotiation`을 지원하며
명시된 파일은 Open마다 읽고 pool의 후속 physical connection은 이미 읽은 TLS 설정을 사용한다. 별도 root certificate가
없는 검증 모드는 Go의 시스템 신뢰 저장소를 따른다. 환경이나 홈에 certificate가 존재한다는 이유로 client 인증을 추가하지 않는다.

명시적인 `connect_timeout`, `target_session_attrs`, `application_name`, `min_protocol_version`, `max_protocol_version`,
`channel_binding`, `require_auth`, `statement_cache_capacity`, `description_cache_capacity`, `default_query_exec_mode`도
드라이버에서 검증한다. 기존 profile-owned startup 값은 URL에 있어도 고정값으로 덮는다. 나머지 옵션과
`service`/`servicefile`/`passfile`은 파일 접근 전에 거부하며 raw parse/TLS 오류와 그 credential·경로를 공개 오류에 보관하지 않는다.

환경 격리·여러 호스트의 포트·TLS material 수명·service 중간 변경·기존 physical profile과 실제 독립 프로젝트
재연결은 별도 검증한다. 작성과 환경별 실행 결과는 [TEST_EVIDENCE](../status/TEST_EVIDENCE.md)에 구분한다.

## 첫 packet 범위

- Scalar/current one-hop relation Query
- Generated Create/Save/update/delete와 callback-bound Atomic
- Current relation read/write subset REL-001..006, REL-009..012
- Model/scalar/FK schema editor operations
- Loaded latest/target/no-op apply/unapply/reapply
- Two-connection/process revision fence and restart resume

## 비목표

- REL-007/008 PostgreSQL project-aware delete와 target-row locking 정책
- Multi-schema tenant, implicit `search_path`, multi-DB/router
- OneToOne/ManyToMany, explicit-key identity sequence reconciliation, upsert/savepoint/public locking AST
- Arbitrary existing database adoption/repair, migration writer/autodetector와 automatic retry
- MySQL/MariaDB/Oracle 또는 production readiness

## 결과

- Backend-specific generated-key/DDL 전략이 core semantic boundary 아래로 내려갑니다.
- SQLite와 PostgreSQL이 하나의 current plan/lifecycle을 공유합니다.
- PostgreSQL dependency와 actual service gate 비용이 늘어납니다.
- Commit unknown, identifier limit, bootstrap/contention과 server restart를 별도 hardening해야 합니다.
